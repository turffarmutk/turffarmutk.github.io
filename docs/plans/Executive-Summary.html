Turf Farm App — Executive Summary

One place to run and see everything happening on the research farm.

We're planning a simple app to bring the daily running of the turf farm into one place. Today, work and information live across whiteboards, spreadsheets, and group texts. The app pulls it together so everyone can see what's happening, what's planned, and what's off-limits — with the farm manager, Bill, as the primary user it's built to help.

Bill assigns the day's jobs to the crew, who check them off as they go. Everyone sees what's done and what's left, live.

Why it helps

  • Protects the research. Plot restrictions are visible on the map before anyone mows or sprays, reducing costly mistakes on trials.
  • Saves Bill time. Assigning work, tracking who's in, and knowing what's in stock all happen in one place instead of many.
  • Keeps everyone informed. Faculty, students, and crew see the same up-to-date picture of the farm.
  • Builds a real record. Chemical applications and farm activity are logged automatically as work gets done.

How the team will use it

It's a phone-first app the crew opens like any website and adds to their home screen — no app store, no installs. Everyone signs in with their UT email, and each person sees a screen tailored to their role: a student sees today's tasks and the map; Bill sees everything. Access is invite-only, so only our team can get in.

1. What this ships

A phone-first task board that closes Bill's daily loop: create a job → get it to a student → student taps it done → Bill sees status at a glance. Jobs can be assigned to a specific student or posted to an open pool anyone can claim. Completion is one tap. Because much of the work repeats, recurring/templated jobs are built in from day one.

Everything updates live — when a student marks a job done, it changes on Bill's screen without a refresh.

4. Task states

Deliberately minimal. Two short lifecycles depending on how the job was handed out:

Assigned to a person:

Open→Done (assignee taps done)

Posted to the pool:

Open (unclaimed)→Claimed→Done (claimer's name shows once grabbed)

5. Core flows

Bill assigns the day's work

Opens the board → taps + New task → picks a task type from the catalog (or free-types one and saves it as a template) → assigns to a person or posts to the pool → sets priority → save. The assignee is notified. Jobs he hands out regularly live in the catalog so he isn't recreating them each time.

Technicians & grad students

See the whole board — everyone's tasks, with live completions and claim/sub-assignment updates — plus the Available pool. They can claim a pool task (their name attaches) or work their self-assigned ones, but can only assign to themselves, never to another person. Finish the job → tap Done; on map-backed jobs they tap off areas on the shared map as they go.

Undergrad students

See only their own assigned tasks — no pool, and they cannot self-assign or claim. They do the assigned work and tap Done (or tap off completed areas on the map). Bill is who assigns them their work.

Opening a map-backed job (step by step)

When a worker taps into the task, it walks them through:

  1. Log the mower — if the job can be done with more than one machine (e.g. Rotary Mow, Greens Mow), they first pick which mower they used. Single-machine jobs skip this step.
  2. The task map opens — for Rotary Mow the map also shows the height of cut the mower should be set to (rotary only).
  3. Restrictions are shown — any active restrictions on whole plots or on specific areas within a plot (where a trial sits) are flagged on the map so the worker steers clear.
  4. Tap plots as they finish — each completed plot is tapped off; progress syncs live so if another student joins they see exactly what's left and where to go next.

Bill checks in

Board shows, live: what's Done today, what's still Open, and what's Claimed and by whom. He can filter by person or by day.

6. Recurring jobs

Most farm jobs repeat, so recurrence is built to save Bill as much time as possible. Any catalog task type — or a job Bill free-types and saves as a template — can be given a repeat schedule (e.g. "Greens Triplex Mow, every weekday," "Rotary Mow → Plots, Mon/Wed/Fri"). The app then auto-creates a fresh task each time it's due, already carrying its map, cut height, and restrictions. Completing today's instance never affects tomorrow's.

No auto-assignment to a person. A recurring job is generated straight into the pool — it is never auto-assigned to someone unless Bill has explicitly pinned an assignee on that template. Since who's on the farm changes day to day (see the crew schedule), this keeps Bill in control of who does what each morning.

v1 keeps recurrence simple: Daily, Weekly on chosen days, or None. Bill can edit or pause a template anytime. (More complex patterns can come later.)

Decided: recurring instances drop into the pool by default; a person is set only if Bill pins one on the template.

7. Screens (v1)

  1. Board / Today — the default. Bill sees all tasks grouped by status (or by person, toggle). Techs/grads see the whole board (everyone's tasks, with live completions and claim/sub-assignment updates) but can only assign to themselves or the pool; undergrads see only their own assigned tasks.
  2. Task detail — full info plus the map-backed work flow (mower log, map, cut height, restrictions, tap-off). Buttons vary by role: complete for the assignee, claim for techs/grads on pool tasks, reassign / edit / delete for Bill. Activity stamp shows who created, claimed, and completed it, with times.
  3. New / edit task — the create form from §3. Hidden from undergrads (only Bill, faculty, techs, and grads can create tasks).
  4. Templates — Bill's list of recurring jobs, with edit/pause. Bill only — hidden from everyone else, including undergrads.

8. Notifications (v1)

Exactly one push notification in v1, kept deliberately minimal so alerts always mean something:

  • Task assigned to you → a push to the assignee (grad students, technicians, and undergrads). This is the only push.
  • New task posted to the pool → no push. Techs/grads see it appear on the board's Available list.
  • Task completed → no push. Bill sees it update live on the board.

Onboarding so notifications actually work

For a PWA, a push won't arrive unless two things happen first — so onboarding, right after a person's first login, walks them through both:

  1. Add to Home Screen — on iPhone, web push only works once the app is installed to the home screen. Onboarding shows the exact Share → "Add to Home Screen" steps (and the equivalent install prompt on Android).
  2. Allow notifications — after install, the app asks for notification permission and confirms it's granted, so "task assigned to you" reliably lands on their phone.

If someone skips or denies it, the app keeps a visible reminder to finish setup, since the assignment push is how the crew learns they have work.

1. What this module does

Undergrads don't all work every day, so Bill needs to know who's coming in and when before he hands out the day's tasks. This module replaces the availability whiteboard: each hourly worker enters their available days and times, logs time off, and can flag a same-day absence. Separately, a time clock records actual punch in/out and totals weekly hours so Bill can cross-check payroll. Together they give Bill a live forward roster that feeds task assignment.

2. Who can do what

RoleIn this module
Undergrad hourly (+ future hourly)Set their own availability (days + times), log time off, send a same-day call-out, clock in/out, see their own schedule and hours
Bill (manager)See everyone's schedule and edit it; see the punch log + weekly hours totals; edit/annotate punches; mark no-shows (Bill-only count)
Technicians / grad studentsView the crew schedule / who's in each day to coordinate work. Do not clock in and do not enter availability (salaried); do not see individual hours
FacultyNot shown — this tile is off their dashboard

3. Availability schedule

The core replacement for the whiteboard, in two layers:

Usual weekly pattern — set each semester

Each worker sets their standing availability — for each weekday, available or not, with a time window (e.g. "Mon 7am–1pm, Wed 8am–12pm, Fri off"). This is what they'd normally write on the board.

Because class schedules change, patterns are tied to a semester — Fall, Winter, and Summer — and must be re-entered each term. At the start of a new term the app prompts each worker to enter their new pattern, and the prior term's pattern is archived rather than carried over.

Exceptions — vacations & conflicts

Any specific date can override the pattern — an extra day, different hours, or a day off. This is where workers enter vacations and one-off conflicts with their usual pattern (a class event, an appointment, a trip). Exceptions win over the standing pattern for that date.

Entry is self-service; every add or change posts an in-app notice to Bill (no push). Bill sees a combined week/day roster of who's available and when, and a "who's in today" summary that drives task assignment.

4. Time off & same-day call-outs

Time off / unavailability calendar

Workers log planned absences over a date range (vacation, travel, exams). These show on a calendar so Bill sees gaps well ahead and can plan around them.

24-hour cutoff — short notice needs Bill's approval

How a time-off request comes off the schedule depends on how close the shift is:

  • More than 24 hours out → self-service. The shift comes off automatically and Bill gets an in-app notice.
  • Within 24 hours of the shift start → it becomes a request Bill must approve. The worker stays on the schedule until Bill approves; on approval the shift is removed. Bill sees pending requests to approve or deny.

Same-day call-out

A quick "I can't come in today" action for sickness or life events. Because it's within 24 hours, it follows the cutoff above — it posts an in-app notice to Bill (no push) and stays on the schedule as a pending request until Bill approves the removal. It's logged the instant it's sent, but it only excuses the day once Bill approves it — an unapproved absence with no clock-in that day becomes a no-show (§5). Workers are still expected to contact Bill directly as well — the call-out is the record, not a replacement for that heads-up.

5. No-show tracking (Bill only)

A day is a NO-SHOW when a scheduled worker never clocks in that day and has no approved absence for it. Bill's approval is the deciding switch:

  • Bill approves the absence → the day is excused and any no-show for it is wiped.
  • Absence not approved (denied or never approved) and no clock-in at any point that day → it stands as a no-show.

Each no-show increments a running count per worker that only Bill sees — a simple accountability tally. The clock-in data does the detecting; Bill's approve/deny decides whether it's excused, so he stays in control.

6. Time clock

Informal presence tracking, not the official payroll record — it gives Bill clean timestamps to cross-check when approving payroll.

  • Who: undergrad hourly + future hourly (role-based, so new hourly staff get it automatically).
  • Clock in / out: one big button on arrival and departure. Location-gated to a 0.5-mile geofence around the farm (35.90203° N, 83.95762° W). A worker can punch multiple times a day — out for lunch, back in — and every in/out pair counts toward the day's hours.
  • Captures: clock-in, clock-out, date, person, and whether the location was verified.
  • Bill's view: the punch log per person plus an auto-summed weekly (Mon–Fri) hours total, side-by-side-ready with the payroll timesheet. Location-unverified punches are flagged for him to confirm.
  • Worker's view: each worker sees their own weekly hours total (not anyone else's).
  • Corrections: Bill can edit or add a missed punch and annotate it.
  • Not doing (v1): calculating pay, enforcing breaks, or acting as the legal timekeeping record.

12. Decisions & open items

Resolved:

  • Clock-in geofence: centered on the farm at 35.90203° N, 83.95762° W (3450 Maloney Rd, Knoxville, TN), 0.5-mile radius. Inside → passes; outside → blocked.
  • If location is unavailable (permission denied, location services off, airplane mode, or poor signal): the punch is allowed but flagged "location unverified" for Bill to confirm — no hard block over a phone glitch.
  • Multiple punches per day: allowed — clock out and back in (lunch, leaving and returning); each in/out pair is its own punch and all count toward the day's hours.
  • Payroll week: Monday–Friday for the weekly hours total.
  • Semester start dates: Fall begins Aug 1, Winter Jan 1, Summer Jun 1 — each triggers the availability re-entry prompt.
When is location "unavailable"? The phone can fail to return a position if the worker denies the location permission, has location services off, is in airplane mode, or is somewhere with poor signal (inside a metal barn) so the fix times out or is too inaccurate. A 0.5-mile radius is generous, so genuine on-site punches almost always pass; the "unverified, flag for Bill" path is the safety valve for the rest.

1. What this module does

The map is where the farm's geography lives. It's an uploaded aerial image with the plots overlaid as tappable regions, and each plot carries data — which mower cuts it, its cut height, any active restrictions, and the trials pinned inside it. Other modules read this map: tasks and field-ops use it to pick where work happened, inventory uses it for spray locations and treated area, and trials place their pins and restrictions here. Get this right and the whole app clicks together.

2. Who can do what

3. Base map & plots

The base is an aerial image Bill uploads — no GPS or satellite service, just the picture of the farm. The uploaded aerial already shows the plot numbering and all plots traced, which is the guide for setup: each plot is turned into a tappable region over the image with its number/name. Regions and pins are stored as coordinates relative to the image, so nothing depends on real-world GPS. The outdoor aerial is a single image and won't be replaced unless the farm expands.

Indoor research plots — a linked second map

Indoor plots get their own separate aerial. On the main (outdoor) map, the building is a selectable region — tapping it opens the indoor aerial, which behaves like the main map (tappable indoor plots, restrictions, pins). The two maps are linked: main → building → indoor.

Reminder — what a "plot" is: a turf area of one grass type; trials and restrictions live inside plots. Non-plot spots (alleyways, borders) are handled with labeled pins (§7).

6. Restrictions on the map

Restrictions (authored in Trial Protocols) render here live. Seven types — No mow, No irrigate, No fungicide, No herbicide, No insecticide, No fertilizer, No wetting agent — each on a whole plot, a spot within a plot (the trial's pin), or a non-plot area, with start/end dates. 4. Counting stock — containers or measured amount

Stock can be viewed two ways, with a toggle to switch between them:

  • Containers — whole units on the shelf (e.g. 3 jugs, 5 bags, 8 cans). Fast to eyeball.
  • Measured amount — volume/weight (e.g. 7.5 gal, 250 lb, 6 lb of seed). Precise for partial containers and applications.

The item's container size converts between the two (1 jug = 2.5 gal → 3 jugs = 7.5 gal). Under the hood a single quantity is stored; the toggle just changes how it's shown, so the two never disagree. Containers can be fractional (a half-used jug = 0.5), since the measured amount is the source of truth. For products with multiple container sizes, the measured amount still rules and the containers view shows the breakdown by size (e.g. 2 × 2.5 gal jugs + 1 × 30 gal drum).

5. Logging usage & restocks

Because the farm carries too many items to label each one, there is no per-item QR. Instead a single shared QR — posted where it's handy (chem room wall, on the sprayer, at the mix station) — opens the logging screen. From there the user picks what they're doing and which product. The same screen is reachable in-app without scanning.

Step 1 — Open the logging screen (two ways in)

So a lost, damaged, or unreachable QR never blocks logging, there are two entry points:

  • Scan the posted QR — fastest at the mix station.
  • In the app — open the Inventory tile and tap Log. Always available to anyone signed in with inventory access.

Either way you land on two big, glove-friendly buttons: Log a spray / usage or Restock.

Step 2a — Log a spray / usage

A short form:

  • Product — a fast search / type-ahead picker over the inventory, with recent products and a category filter pinned up top since the list is long. This is what replaces scanning a specific item.
  • Amount used (required) — number + unit, with the containers/measured toggle; decimals allowed. Mandatory, so stock always decrements by a real figure.
  • Where — opens the interactive map; the person taps the plots they sprayed (a "plot" = a turf area of one grass type; trials and restrictions live inside plots). This records the exact plots and auto-sums the total area treated from the map's plot sizes. When logging from a task, the plots pre-fill from that task.
  • Who / when — auto-filled from login and the current time (both editable).

Save → stock is decremented by the amount, and the entry (product, amount, plots, area, who, when) also feeds the chemical-application record.

Depends on the interactive map: the "where" picker and the treated-area total both read from the interactive maps module — plots and their sizes come from there. Until that module is built, "where" falls back to picking plot numbers from a list, without the automatic area total.

Step 2b — Restock

An even shorter form:

  • Product — same search picker; if it's brand-new, + Add product opens item setup with brand-name autofill (§3).
  • Container size + quantity received — pick which size came in (for mixed-size products), then the number of containers (usually whole); auto-converted to a measured amount.
  • Who / when — auto-filled, editable.

Save → stock is incremented. Every movement — usage or restock — is stamped with who, what, how much, and when.

5. Chemical application record

Any pesticide/fertilizer op is automatically part of the chemical application record — a compliance view kept in the log (a formal export/report is a later add). Only people allowed to make chemical applications can create these entries (§2). For v1 it captures: product, active ingredient, amount used, rate, target pest/weed, plots/area treated, applicator (the logged person), and date/time. Area treated is summed from the selected plots (interactive map). Fields like EPA reg #, REI/PHI, applicator license, and weather are noted for later (§9).

6. Relationship to tasks & inventory (important)

This log is the single operations record — tasks and inventory feed it so nothing is entered twice:

Inventory (sprays & fertilizer)

A chemical/fert op records a product + amount, which decrements the product's stock. It's one event: the field-ops entry and the inventory decrement are the same record, so stock drops once and is never double-counted.

Tasks (mowing auto-log)

Completing a mow task posts a field-ops entry here automatically — completing the task and logging the mow are the same record, no double entry.

Decided: field-ops is the one true operations log; task completion and inventory logging feed into it. The source field (manual / task / inventory) records how each entry arrived.

1. What this module does

Gives the team the weather that matters for turf work: current conditions and a forecast, a rainfall log for irrigation decisions and records, and growing-degree-day (GDD) tracking for timing models. It runs off a weather API at the farm's coordinates — no on-site hardware — and shows an in-app frost/freeze warning when a freeze is coming.

2. Who can do what

RoleIn this module
Everyone signed inView current conditions, forecast, rainfall log, GDD, and the frost/freeze warning
Bill (manager)Configure settings — GDD base temp & start date, frost threshold (§7)

3. Data source

A weather API keyed to the farm's location — 35.90203° N, 83.95762° W (3450 Maloney Rd, Knoxville, TN). The app pulls current conditions, forecast, and precipitation on a schedule and caches them, so the tile loads instantly and keeps history for the rainfall log and GDD.

To pick: which weather service. The US National Weather Service API (weather.gov) is free and covers the farm; commercial options (OpenWeather, Visual Crossing) add features. Choice affects cost and which fields are available.

4. Current & forecast

The default view: right now (temperature, conditions, wind, humidity) and a multi-day forecast (highs/lows, conditions, precip chance). Units in °F, mph, inches.

5. Rainfall log

A running record of rainfall over time, built from the API's precipitation data — daily totals rolling up to weekly/monthly, viewable as a history and chart. Useful for irrigation calls and for the record of how much water a plot has had.

To confirm: allow a manual rain-gauge override so Bill can correct the API figure with an actual on-farm gauge reading? (Improves accuracy; small add.)

6. Growing degree days

GDD accumulation for timing models (PGR reapplication, pest/weed emergence). Computed daily as average temp − base temp (floored at zero) and accumulated from a start date. The base temperature and start date are configurable, since different models use different bases.

To set: which base(s) and start — e.g. base 32°F or 50°F, from Jan 1 or a biofix date. v1 can support one configurable GDD track; multiple named models could come later.

7. Frost / freeze warning

When the forecast low drops to or below the frost threshold, the weather tile shows an FROST / FREEZE warning so the team can protect turf. In-app only — no push, consistent with the app's minimal-push approach. Bill sets the threshold (default at/near 32°F).

8. Screens (v1)

  1. Weather — current conditions + forecast, with the frost/freeze banner when applicable. Default screen.
  2. Rainfall — the rainfall history/chart.
  3. GDD — accumulation value and chart, with the base temp shown.
  4. Settings — GDD base temp & start date, frost threshold. Bill only.

10. Out of scope for v1 (comes later)

  • Spray-window indicator (wind/temp legality flags)
  • Evapotranspiration (ET), soil temperature, soil moisture
  • Push alerts of any kind (frost is in-app only)
  • Multiple named GDD models at once

11. Open questions

  1. Weather service: free NWS (weather.gov) vs a commercial API — which fields and cost.
  2. GDD base & start: which base temp(s) and start date (or biofix) to use.
  3. Frost threshold: exact value — right at 32°F, or a few degrees above for a margin.
  4. Rain-gauge override: allow a manual correction to the API rainfall figure?
