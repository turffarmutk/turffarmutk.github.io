1. The one-line goal

A mobile-first, real-time hub for everything happening on the UT Turfgrass research farm — so Bill (farm manager) always knows what work is happening, what's planned, what's in stock, and which plots are off-limits, and so the whole team logs and sees activity in one place instead of paper, spreadsheets, and group texts.

Bill is the primary user. If a feature doesn't make Bill's day easier or protect the research, it waits.

Permission model (starting proposal): everyone can see almost everything (transparency is the point). Editing is scoped — you can edit your own group's trials and any task assigned to you; only Bill + faculty can override plot restrictions or delete records. Undergrads are log-and-complete only.

Open Q: Should faculty see other labs' full trial details, or just summary/restrictions? Turf research groups sometimes guard in-progress work.

3. Core modules

Ordered roughly by priority. MVP = Module 1 + the read side of 2, 3, and 5.

Module 1 — Daily Task Board MVP core

The heart of the app.

  • Task board: Bill (or a PI) creates tasks from the farm task catalog — "Rotary Mow → Alleys," "Spray Pesticide (Backpack) → Fungicide," "Fix reel on Toro 3." Assign to a person or post to the pool, set priority, attach plots/map. Assignee checks it off; map-backed jobs tap plots off live. See the Task Board spec.

Module 2 — Field Operations Log

Structured logging for recurring farm work, tied to a field/plot: mowing (height, direction), fertilization, pesticide/herbicide application (product, EPA reg #, rate, area, applicator, REI/PHI, weather), irrigation, cultivation, seeding/overseeding, topdressing. Getting chemical apps clean means audit-ready spray records fall out for free.

Module 3 — Research Trials + Plot Map

  • Visual plot map of the farm — a grid/blocks you can tap to see what trial lives there.
  • Trial records: PI, group, treatments, reps, start/end dates, objective.
  • Plot restrictions (huge for Bill): flag a plot/trial "do not mow / spray / irrigate," with dates and a reason. Surfaces loudly to crew before they touch that area.

Module 4 — Real-Time Inventory You flagged this

Live stock list so Bill isn't caught short. Categories to confirm: chemicals (link to spray log so applying a product auto-decrements stock), fertilizer, seed, fuel, sand/topdressing, parts/consumables, maybe PPE. Each item: quantity on hand, unit, location, reorder threshold → low-stock alert.

Module 5 — Study Planning / Upcoming Studies You flagged this

Faculty and grad students submit a planned study before it starts: proposed plots, timing, and what they'll need from the farm (mowing regime, irrigation, spray windows, equipment, materials). Bill gets alerted in advance and sees a forward calendar, can flag conflicts (two groups wanting the same plots), and prep. Turns surprises into a pipeline.

Module 6 — Equipment & Maintenance

Roster of mowers, sprayers, tractors, utility vehicles. Status (available / in use / down), who has it, maintenance log, and "report a problem" → auto-creates a task. Can start as a simple status board and grow.

Module 7 — Weather & Conditions

On-farm weather station feed if one exists, otherwise a weather API for the farm's location. Rainfall, growing degree days, and spray-window indicators (wind/temp). Feeds decisions in Modules 2 and 5.

Module 8 — Notifications cross-cutting

Push + in-app alerts: task assigned to you, activity on your trial's plots, a new/edited plot restriction, planned-study submitted, low inventory, equipment down, weather/frost. Everyone sets what they want to be pinged about. Note: on iPhones, users must add the app to their home screen before web push works — we'll build a friendly "install me" prompt into onboarding.

4. What "real time" means here

  • Live updates: when someone logs an event, it appears on everyone's board without refreshing.
  • Push notifications to phones for the alert types above.
  • Connectivity is decent at the farm, so we assume mostly-online for v1 (no heavy offline-sync engineering). Forms stay forgiving of a brief drop.

5. Why a PWA, not a native app

Recommendation: build this as a Progressive Web App (PWA) — an installable web app that lives at a URL and can be added to a phone's home screen. It satisfies every module above, including push notifications, without the cost of native.

What a PWA gives us

  • Mobile-first, installs to the home screen, feels like an app
  • Real-time live updates
  • Camera / photo uploads
  • Push notifications — including on iPhone (iOS 16.4+), once added to the home screen
  • One codebase, instant updates for everyone, no app-store review
  • No Apple/Google developer accounts or install friction for ~25 users

Where native would be stronger — and whether it matters

  • Offline-first: possible in a PWA but real work; signal is decent at the farm, so not needed for v1.
  • Deep hardware (NFC tap, Bluetooth sensors, background GPS): not on the roadmap. QR-code scanning via the camera works fine in a PWA.
  • App Store listing: unnecessary for an internal team tool — a URL is simpler.

Cost comparison

ItemPWANative (iOS + Android)
Codebase / build effortOne codebase for all phones and desktopTwo native apps, or a React Native/Flutter rewrite — more build time
App store feesNoneApple $99/yr + Google $25 one-time
Hosting & backendSame either way — a managed backend (Supabase/Firebase) free tier likely covers ~25 users, or roughly $0–25/mo as it grows; object storage for photos is pennies/GB
Domain name~$12/yr (optional — could live on a UT subdomain for free)~$12/yr
Updates / maintenancePush a change, everyone has it instantly — no reviewApp-store review cycles; users must update the installed app

The dominant cost in both cases is developer time, and native roughly multiplies it. Recurring cash cost for a PWA at this scale is close to zero — realistically just a domain, since the free tiers comfortably fit 25 users.

Bottom line: going native would mostly buy an App Store listing, offline-first, and deep hardware access — none of which the current plan needs — at the cost of two codebases, store fees, and slower updates. A well-built PWA can be wrapped or migrated to native later if a real need appears; the backend and most of the UI carry over.

6. Data security & access

Key reframe: a PWA is exactly as protectable as a native app, because nearly all real security lives in the backend, database, and login — not the app on the phone. Protection stacks from the outside in:

LayerHow we protect it
TransportEverything runs over HTTPS (required for a PWA). Data in motion is encrypted — nobody on farm wifi can sniff a record.
Login / identityv1: magic-link email sign-in (a one-time link to a UT inbox) with an invite-only roster — no passwords stored by us. Delivered via managed auth (Clerk, Supabase, Firebase, Auth0). Institutional single sign-on can be added later. We never roll our own password storage.
AuthorizationRoles are enforced on the server, never trusting the app. Every request independently checks "is this person allowed to do this?" — this is what actually keeps someone from reaching another lab's private records.
Data at restLives in a managed, encrypted database — not on anyone's phone. The app caches only recent screens, and sensitive fields are kept out of that cache.
The deviceThe realistic threat is a lost/borrowed phone, not a hacker. Mitigations: expiring sessions with re-login, a visible log-out, and a "sign out everywhere" for Bill. No unencrypted app bundle sits on the device.
Audit trailEvery action is already logged, so security auditing comes free — every edit is stamped with who and when, and is traceable/reversible.
Decisions this raises:
  • Auth (decided): magic-link email sign-in + invite-only roster for v1; institutional SSO can be added later as an extra sign-in method.
  • Is anything sensitive? If a trial's details carry confidentiality terms, tighten per-lab visibility. Otherwise a standard managed cloud stack is plenty.

7. Storage & scale

Two different "storages" hide in this question, and separating them is the whole answer.

On-device (browser) storage

Modest and browser-controlled. iOS/Safari is the tightest (~1 GB per app, and it can evict cached data — though a home-screen-installed PWA is protected from automatic eviction). We never rely on it. It's just a cache for recent screens and maybe a queued entry during a brief signal drop. If wiped, nothing is lost.

Backend database (system of record)

The real data lives on a server, not on any device — and this is what determines whether user count or volume is ever a problem. For this farm, it never is.

Will we hit limits from users or data entered? No — by a wide margin. ~25 people, only a handful entering at once. Each record (a spray log, task, inventory change, turf rating) is well under a kilobyte. Even years of aggressive daily logging is tens of thousands of rows a year — a managed Postgres database handles millions without noticing, and these stacks serve thousands of simultaneous users. 25 is trivial.

The one thing that consumes real storage is photos — so they don't go in the database. Images go to object storage (S3, Cloudflare R2, Supabase Storage, Firebase Storage), which is effectively unlimited at pennies per gigabyte; the database just stores a link. Do that, and years of equipment and turf photos are a non-issue.

The only decision this surfaces is where the backend lives: a managed backend-as-a-service (Supabase or Firebase — database + auth + file storage + real-time in one bundle, fastest path, cheap tiers that fit easily), or self-hosting if the team prefers. Both handle the volume with room to spare; the choice is about maintenance, not capacity.

8. Build phases

Foundation-first order, so each piece has what it needs. (Auth + roles come with Phase 1, since login gates everything.)

1

Interactive map

Upload the aerial, trace the plots + numbering, set each plot's mower and cut height, add the indoor map. Plus auth + roles. The foundation every other feature points to.

2

Current trials + restrictions

Load the active studies and their plot restrictions onto the map, so it protects the research from day one.

3

Task board

Catalog-based task assignment, the crew's check-off, and map-backed mowing jobs. The daily engine.

4

Inventory + crew scheduling

Real-time inventory with low-stock alerts and QR logging, plus the availability board and time clock.

5

Round it out

Equipment/maintenance, weather feed, and the fuller field-operations record.
